Not in the top 10, on purpose:
- **Post metrics.** `metrics`/`aggregatedPostMetrics` need `insightsRead`, which "an App Client cannot request through OAuth" ([Post Metrics guide](https://developers.buffer.com/guides/post-metrics.html)). `CONTEST.md` is right that apps can't read them. An optional "paste your personal key" mode would work technically, but it sidesteps the OAuth story the judges asked for.
- **Webhooks.** The public API has none. "realTime (webhook/firehose)" in `SyncDataMechanism` describes Buffer's own engagement sync, not a subscription API. Keep polling `posts(status: sent|error)` with the 30 s cache.
- **agent-desktop.** See §1.

## 1. vercel-labs/agent-desktop

Source: https://github.com/vercel-labs/agent-desktop (README, CHANGELOG, GitHub API).

- **What it is.** "Computer use for AI agents: read and operate desktop apps through the OS accessibility tree." A Rust CLI plus a C library (FFI) for macOS, Windows and Linux. `snapshot` returns JSON with a ref per element, the agent acts on a ref (`click @s…:e8`), then snapshots again. 56 working commands (observe, click/type, keyboard/mouse, windows, notifications, clipboard, screenshot, `batch`). Headless by default through the accessibility API.
- **License.** Apache-2.0.
- **Maturity.** Created 19 Feb 2026, about 11.4k stars, 778 forks, 136 open issues, pushed 3 Nov 2026. **v1.1.0 shipped 2 Nov 2026 with breaking changes** (C ABI major 7, envelope 2.6, refs now carry a "capture proof"). It works and is moving fast, and the API surface still churns.
- **Fit for us.** Two possible uses, both **No**:
  - *Drive Buffer's or Instagram's UI for what the API lacks (carousel music etc.).* It operates **native desktop apps** through accessibility APIs, not websites. On Linux it needs "the user's graphical session with at-spi2-core", and mouse input needs X11 with `--headed`. Our sandbox and Render have no desktop session. Automating Instagram's UI also breaks Meta's automation terms and puts the user's account at risk. Buffer itself can't attach music to an automatically published post. The honest route is the reminder flow in item #7.
  - *390 px UI QA screenshots.* Wrong layer: it screenshots OS windows. The right tool for web screenshots is its sibling **vercel-labs/agent-browser** ("Browser automation CLI for AI agents", Apache-2.0, about 45k stars, https://github.com/vercel-labs/agent-browser), or the Playwright set-up we already have (`scripts/responsive_audit.py` and `tests/studio/test_responsive.py` already check 360/390/768/1024/1440 px). When the sandbox lacks Chromium, run the audit in GitHub Actions (studio-ci) and upload the PNGs as artifacts. No new dependency needed.
- **Verdict: No.** The one best use, if we ever ship a native wrapper, is local macOS QA of a desktop app. For the contest, put the time into item #8 or a CI screenshot artifact instead.

## 2. Rerun (rerun.build)

Sources: https://rerun.build/ and https://github.com/rerun-build/rerun (README, GitHub API).

- **What it is.** "AI coworkers that run your work." You describe a job, a "Foreman" plans a team of agent coworkers, and each gets memory, skills and its own cloud computer (browser + screen you can watch and take over). It runs on schedules or webhook triggers, uses 3,000+ tools/any MCP, and "stops before anything consequential". Next.js, Supabase, Vercel AI SDK, Hono, libSQL, Patchright, Docker.
- **Open source?** Yes. **AGPL-3.0** (repo created 29 Oct 2026, about 370 stars). HuhQueue is **MIT**, so **borrow ideas only, copy no code** (AGPL would force our hosted app's source under AGPL). The name and logo are trademarked separately.
- **Ideas worth borrowing (concrete):**
  1. **Routines with a trigger URL.** "Every weekday at 07:00" or "when an app calls the webhook". For us: a per-user inbound webhook (`POST /api/hooks/{token}`) that starts a "Make a post" run from a URL (new blog post, GitHub release, RSS item), plus a cron "every Monday, plan the week from my feeds". Agents and Zapier/n8n can then drive HuhQueue. (M)
  2. **Rules that answer approvals for you.** "You can also leave it rules to answer by itself, so it only waits on the calls you want to make yourself." For us: per-agent auto-approve rules, e.g. "auto-approve if the brand check passes, there are no preflight warnings and it's a draft". It builds on the existing `review/draft/trusted` policies and the Style Ledger. (S–M)
  3. **Cost shown before running.** "Before a search, your Coworker tells you what it will cost and waits for your yes." For us: the preview shows "≈3 AI calls, 1 Reel render (~90 s), 5 Buffer requests of your 150/15 min" from `RateBudget` and the free quota. (S)
  4. **One board, live.** Every coworker and run is on one real-time board, with full history per run. Our Activity and runs could become a live board with run cards (status, current step, elapsed time, retry). (M)
  5. **Take over mid-run.** "Open its screen… fix the field it got wrong, then hand it back." For us: pause a run at the review step, edit the caption or slide, then "Continue" resumes from that step (needs item #8's step checkpoints). (M)
  6. **Model per job.** "The fast cheap model for sorting… the strongest one for the job that has to be right." For us: a cheap model for summarising and scoring, a strong one for the final caption, set per engine in AI settings. (S)
  7. **Template gallery as a "hire" flow.** Ready-made coworkers per trade. For us: "Recipes" such as *Blog → week of posts*, *Podcast → 5 clips*, *Product launch → carousel + thread*, each one click into a prefilled run. Good for the demo video. (S)
  8. **Told when something goes wrong.** A failed run, a question or a lost connection reaches you by email/notification. For us: an email or web push when a Buffer post errors (we already show it in the Inbox). (M)

## 3. Open WebUI: chat UX worth copying (for the chat-UI agent)

Source: https://docs.openwebui.com/features/. Open WebUI ships under its own "Open WebUI License" (https://docs.openwebui.com/license), so take ideas, not code.

- **Message queue**: keep typing while the AI responds, and messages send automatically.
- **Slash-command prompts with typed variables** (`/carousel {url} {tone}`) and **`@` mentions** to call a tool or model (`@clipper`, `@brandcheck`).
- **Side-by-side compare** of two models' outputs: two caption variants side by side, pick one.
- **Inline approvals, tables and files** in the thread. A post preview card with Approve / Edit / Schedule right in chat.
- **Visible task list** for multi-step runs (a model-maintained checklist), with live tool steps and citations to sources (the article URL).
- **Folders, tags and pins** on conversations. Voice input (speech-to-text).
- **Model controls preset** (pick "fast / best") in the composer rather than in settings.

Rate limits (from the [Rate Limits guide](https://developers.buffer.com/guides/api-limits.html)): app client base 100 / 15 min, 500 / 24 h, 15,000 / 30 d, **plus 10 / 25 / 100 per authorised user** (up to 1,000 users). ## 5. Efficiency and reliability ideas (concrete for this repo)

- **Prompt caching.**
  - Anthropic: add top-level `"cache_control": {"type": "ephemeral"}` in `llm.chat()` for the `anthropic` style. Put the stable part (system rules + brand kit + Style Ledger rules) first and the article/user text last. Reads cost 0.1× base input, 5-minute writes 1.25×. Minimum cacheable prompt is 1,024 tokens on Sonnet 4.5 (our preset `claude-sonnet-4-5`), so a short prompt simply won't cache, with no error ([Anthropic docs](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)).
  - OpenAI: caching is automatic for supported models once the prefix is long enough. Keep the prefix byte-identical (no timestamps up top) and pass a stable `prompt_cache_key` per user/workspace on pre-5.6 models like our `gpt-4.1-mini` preset ([OpenAI docs](https://platform.openai.com/docs/guides/prompt-caching)).
- **Result cache.** Key = sha256(normalised article text) + brand-kit version + ledger version + model + prompt version. "Regenerate" bypasses it. It saves the free quota (`FREE_DAILY = 40`) and makes demo re-runs instant.
- **Render cache.** Content-address slides and cards: hash(template, text, kit colours/fonts, logo hash, ratio) → stored JPEG, so editing one slide re-renders one slide. FFmpeg already uses `-preset veryfast`. For slideshow Reels, encode each slide segment once and concat with `-c copy` when only one slide changes.
- **Buffer request budget.**
  - One bootstrap query (`account` + `channels{…postingSchedule…}` + `dailyPostingLimits`) instead of today's separate `channels`, `org_limits`, `posting_schedules` (which re-queries `channels`) and `daily_limits` calls.
  - Aliases for multi-channel limit checks (≤ 30).
  - `createContentItem` instead of N `createPost` calls.
- **Run resume.** On boot, select `agent_runs` and take runs in `running`/`rendering` with `updated` older than N minutes. Then:
  - mark the in-flight step `interrupted`;
  - re-enqueue from the last `done` step (steps are already stored as JSON per run);
  - make the publish step idempotent: write a `(run_id, channel_id) → buffer_post_id` row right after `createPost`/`createContentItem` returns, and skip channels that already have one on retry.
- **Queue reliability.** Move long work (renders, research) off the web dyno's in-process pool, the way One take already does with the GitHub Actions worker, or at least cap it with a heartbeat column so the Inbox can show "stalled, Retry".
- **Media durability.** Buffer fetches media **at publish time** ([Hosting Media guide](https://developers.buffer.com/guides/hosting-media.html)), so our rendered-media URLs must stay up until `sentAt`. Add a retention rule ("keep until the post is sent + 7 days") and a preflight check that our own media URL answers 200 before `dueAt`.

## 6. Judges' criteria (Buffer Commit)

Sources: https://buffer.com/api/commit and the [Builder handbook](https://buffer.notion.site/Buffer-Commit-Developer-Handbook-3d7a7f5a00fd80918466e36eb2cba9f8).

- **Scoring.** Three judges, Joel Gascoigne (CEO), Amanda Marochko (Staff PM) and Joe Birch (Staff Engineer), score on **usefulness, execution and craft, and creativity**.
- **The ask.** "Build a web app or an integration that makes creating and publishing content noticeably better, using the Buffer API to power at least one of its core features… a capability Buffer doesn't have yet or a bridge."
- **Eligibility.** Works end to end through **Buffer OAuth** with real API calls. Publicly available at submission and through judging. For existing projects, only the work added during the window is judged (our `CONTEST.md` already separates this).
- **Submission.** App + write-up + **demo video link** by **13 Nov 2026, 23:59 PT** (14 Nov, 07:59 Dublin time). Judging starts 16 Nov, winners on 7 Dec.
- **Extra awards.** *Delight* (most distinctive UX, picked by the design team) and *Build-in-Public* (shared the build most openly). Posting progress on X/LinkedIn through HuhQueue itself would count toward both.
- **Implications.**
  - Lead the demo with one link → a branded week in Buffer in under 2 minutes.
  - Show Buffer-native depth: tags, first comment, AI disclosure, ideas, content items. A Buffer engineer will notice these.
  - Keep the public URL warm through December.
