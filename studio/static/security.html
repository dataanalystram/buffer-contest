Security

Security

How HuhQueue protects your Buffer connection, your data and what your agents can do. The threat model and audit results are public.

Last updated 3 November 2026Applies to huhqueue-studio.onrender.com

In short

Encrypted secretsBuffer tokens and your own AI keys are sealed at rest and stay on the server.
Strict browser policyOur own scripts only, no framing, a CSRF header on every write.
Agents on a leashHashed scoped tokens, approval by default, caps and a kill switch.
Outside content is dataPages and feeds are fenced as untrusted; sensitive actions wait for you.

Signing in

  • Buffer OAuth 2.0 with PKCE; the session id is rotated at sign-in.
  • Session cookie: HttpOnly, Secure, SameSite=Lax. Every write also needs a CSRF token sent in a header.
  • Sign-in always opens as a full page in your browser, never inside a frame.

In your browser

  • Content Security Policy: scripts only from this site, no inline scripts, no third-party scripts or fonts, object-src 'none', frame-ancestors 'none'.
  • X-Frame-Options: DENY, X-Content-Type-Options: nosniff and a strict Referrer-Policy.
  • Text from outside (feeds, websites, filenames, captions) is escaped before it is shown, and links from outside open only web addresses, never javascript:.

Your data

  • Buffer tokens and your own AI keys are sealed with Fernet encryption under a dedicated server key (TOKEN_KEY), which can be rotated, and are never sent to the browser.
  • Agent tokens, session ids, sign-in codes and device links are stored only as hashes.
  • AI logs keep metadata only, never prompts, replies or keys. Activity rows are deleted after 90 days and sign-in IP addresses and browsers are cleared after 30.
  • Disconnect and delete removes every table that holds your data at once.

AI apps and agents

  • Each token has a policy (approval, drafts only or trusted), a daily cap and an expiry, and can be revoked.
  • The kill switch and caps run before every agent action, over MCP and REST.
  • The MCP sign-in screen shows where it will send you back and flags unverified apps, which can't be given trusted access.
  • Prompt injection: pages, feeds and other outside content are fenced in prompts as untrusted data. Once the agent has read outside content, sensitive tools (send, schedule, delete) are held for your confirmation. MCP clients are told that tool results carry outside content and must be treated as data, not instructions. This lowers the risk; no defence against prompt injection is complete, which is why posts wait for approval by default.
  • The sample workspace at /demo is view-only: actions that would change data answer "In the real app this would…" and nothing is saved or sent.

On the server

  • Every outbound fetch goes through one safe-fetch helper that re-checks each redirect against private, loopback and metadata addresses.
  • Request bodies are size-capped before parsing; anonymous and sample traffic is rate- and cost-limited.
  • Video workers authenticate with a GitHub OIDC identity and a single-use job token; no token appears in workflow logs.

Checks on every change

gitleaks secret scanning, pip-audit on dependencies, the full test suite on SQLite and Postgres, and a real-browser smoke test. The threat model, past audit findings, their fixes and known limits are in docs/SECURITY.md.

Report a vulnerability

Please report security problems privately through GitHub: Report a vulnerability (private vulnerability reporting is on). Don't open a public issue for a vulnerability. Test only against your own account or the /demo sample workspace. The policy, scope and response times are in SECURITY.md. For anything else, open an issue on the project's GitHub or message @huhbyte.ai on Instagram.
